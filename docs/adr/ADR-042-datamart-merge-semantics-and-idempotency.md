# ADR-042 — Datamart merge semantics and idempotency key

- Status: **ACCEPTED** (Session 22)
- Related: ADR-040, ADR-043, `docs/FOUR_FLOWS.md`

## Context

Two idempotency mechanisms exist in the references.

**Repo 2 rewinds the target.** Before recomputing, it reads `auto_correct_snapshot_id` for
the previous run of the same `execution_date` and calls
`CALL spark_catalog.system.set_current_snapshot('dlpt.<tbl>', <id>)` across eight target
tables (`f_acct_depo_by_day_level_acct_auto_correct_generate.py:194-215`, with two more
rewinds at `:493` and `:618`), then appends the new snapshot ids for the next run
(`:1390-1415`).

**This repository guards the MERGE.** `spark/common/flows.py:127 may_overwrite` and
`:150 merge_condition_sql` implement an accuracy ladder — a higher tier always wins, and
within a tier the later `input_cutoff` wins — with a test asserting the Python and the
generated SQL agree on every ordered pair of statuses.

Repo 2's mechanism discards anything committed to those tables between the two runs, has
no recovery path if the process dies mid-rewind, and is unsafe with any concurrent writer.

**Repo 6** shows the third-party shape: `iceberg_upsert_by_primary_key`
(`sparknode/writer.py:1013`) emits `MERGE INTO ... WHEN MATCHED [AND target.<hash> !=
source.<hash>] THEN UPDATE ... WHEN NOT MATCHED THEN INSERT` — an optional hash column as
a change-detection short-circuit.

## Options

| Option | Verdict |
|---|---|
| **Guarded MERGE on the accuracy ladder (this repo, extended to five modes)** | **CHOSEN** |
| Snapshot rewind before recompute (repo 2) | Rejected |
| Plain `insert_overwrite` by partition | Rejected as the general case |

## Decision

**Every reporting mode writes through one guarded MERGE.** The ladder is extended to the
five modes with no new tiers:

| Mode | Stamps | May overwrite |
|---|---|---|
| `STREAMING_RT` | `PROVISIONAL_NRT` (1) | nothing higher |
| `STREAM_BATCH` | `PROVISIONAL_NRT` (1) | nothing higher |
| `AUTO_CORRECT` | `PROVISIONAL_CORRECTED` (2) | NRT, not CERTIFIED |
| `EOD` | `CERTIFIED` (4) | everything; a later EOD wins on `input_cutoff` |
| `FULFILL` | tier of its source layer | per the same rule |

The `WHEN MATCHED AND ...` predicate is generated by `merge_condition_sql()`, not written
by hand in any model — a second hardcoded copy is how an anti-downgrade rule stops matching
the ladder it enforces.

**Two idempotency keys, deliberately distinct:**

| Key | Scope | Purpose |
|---|---|---|
| `(job_id, flow_mode, date_of_data, attempt_number)` | **execution** | uniquely names one attempt; PK of `job_master_execution_hist` |
| `(job_id, flow_mode, cob_date)` | **data** | rerunning this triple must converge to the same mart state |

Data idempotency does not require the execution key to repeat. A rerun is a *new* attempt
that re-merges the same logical output; the ladder plus `input_cutoff` makes the result
identical regardless of how many attempts preceded it.

**Per-mart write contract**, mandatory in `job_master`:

```yaml
primary_key: [account_sk, business_date]   # the MERGE key
business_date_column: business_date
partition_spec: [business_date]            # never a PK or high-cardinality column
merge_strategy: MERGE_LADDER               # | INSERT_OVERWRITE_PARTITION | APPEND
delete_strategy: SOFT | HARD | NONE
```

`INSERT_OVERWRITE_PARTITION` is permitted only where the mode owns the whole partition —
in practice `EOD` and `FULFILL` on a mart with no intraday writer. Compile **fails** if a
mart declares `INSERT_OVERWRITE_PARTITION` while also enabling `STREAM_BATCH` or
`AUTO_CORRECT`, because an overwrite would silently erase provisional rows the ladder
exists to protect. The current `dbt/dbt_project.yml` sets
`+incremental_strategy: insert_overwrite` globally; that stays valid only for marts with a
single writing mode, and the compiler enforces it.

**Iceberg snapshot ids are recorded, not used for control.** `iceberg_snapshot_id_before` /
`_after` are captured per input and output table into `job_master_execution_hist`
(`MAP<STRING,BIGINT>`) — repo 2's idea kept for audit and for a deliberate operator-driven
rollback, never as the automatic rerun mechanism.

**`CLAUDE.md` §6 partitioning rule is enforced at compile**, with one carve-out that the
first wording of this ADR got wrong and Phase 3 implementation caught:

| `partition_spec` contains | Verdict |
|---|---|
| a column marked `high_cardinality_columns` | rejected, always |
| a primary-key column that is **not** `business_date_column` | rejected |
| `business_date_column`, **even when it is part of the composite PK** | **allowed** |

The carve-out is not a softening. `mart_account_balance_daily` has grain
`(account_sk, business_date)` and is `PARTITIONED BY (business_date)`
(`spark/common/ddl/kimball.sql:182`); so does every other daily mart in this repository.
A flat "no PK column in the partition spec" rejects the repo's own deployed DDL. What the
rule actually protects against is a partition whose cardinality approaches the row count —
one file per row, and a table that is unqueryable long before anyone reads the spec. The
business date is the opposite of that.

Corrected 2026-08-19 during Phase 3; the original wording is retained here rather than
silently replaced, because the defect is instructive: a rule stated over the wrong
attribute (membership in the PK) instead of the real one (cardinality).

## Consequences

- A late `STREAM_BATCH` run can never downgrade a certified figure.
- Concurrent modes on one mart are safe; repo 2's design is not.
- A stale rerun of the same tier loses to the newer `input_cutoff` rather than winning.
- dbt models do not author the merge predicate; `merge_predicate.sql` wraps it.

## Cost

MERGE is more expensive than an append. Bounded by `partition_spec` + the flow window, and
by `cost_guard.max_bytes_scanned_gb` per mode.

## Security

None.

## Rollback

`merge_strategy` is per-mart config. Switching a mart to `INSERT_OVERWRITE_PARTITION`
requires disabling its intraday modes first, which the compiler enforces in both
directions.

## Validation

- The existing ladder test is extended to all five modes: `may_overwrite()` and
  `merge_condition_sql()` agree on every ordered pair.
- A `STREAM_BATCH` run after an `EOD` run leaves the certified rows unchanged.
- A stale rerun (older `input_cutoff`, same tier) does not overwrite.
- Running the same `(job_id, flow_mode, cob_date)` three times produces byte-identical
  mart content (checksum comparison, as `test_l3_snapshot.py` already does for L3).
- Compile fails on `INSERT_OVERWRITE_PARTITION` + an intraday mode.
- Compile fails on a `partition_spec` containing a PK column.
