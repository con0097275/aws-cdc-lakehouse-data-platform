  `slice(data.aws_availability_zones.available.names, 0, var.az_count)`

  so changing it changes the PROVIDER configuration; the data source is then re-read at

  cascades into MSK, EMR and all three EC2 instances.

  ADR-027 REQUIRES updating auto_destroy_after for each new window. Following that rule
  today destroys and recreates the Kafka cluster, losing every topic and all CDC state.

  Not fixed here: pinning the AZs (e.g. an explicit az_names variable, or ignore_changes on
  availability_zone) changes network identity and belongs in a reviewed decision.

BLOCKER 2 — the untargeted plan SILENTLY REVOKES TWO MSK INGRESS RULES
--------------------------------------------------------------------------------
  Even with auto_destroy_after left alone, the 1 remaining `update` is:

    module.kafka_platform[0].aws_security_group.msk

  and the diff REMOVES two ingress rules on port 9098:

    "MSK IAM SASL from EMR Serverless workers"   (sg-073bcf5116a43f851)
    "MSK IAM SASL from the CDC runtime"          (sg-068cb5490766980c5)

  Cause: `aws_security_group.msk` declares INLINE `ingress` blocks, while the rules above
  are separate resources in other modules --

    module.emr_serverless[0].aws_vpc_security_group_ingress_rule.msk_from_emr
    module.cdc_runtime[0].aws_vpc_security_group_ingress_rule.msk_from_cdc_runtime

  The AWS provider forbids mixing the two styles on one security group: the inline block is
  authoritative and revokes rules it does not know about. The separate resources are in
  state and unchanged, so they are NOT re-added in the same apply -- EMR Serverless and the
  CDC runtime would lose Kafka access until a subsequent apply restored it.

  That is the exact path Phase 14's CDC pipeline runs on.

  Not fixed here: converting the inline rules to separate resources on a LIVE security
  group in front of a running MSK cluster is a reviewed change, not a side effect of
  unblocking a test.
