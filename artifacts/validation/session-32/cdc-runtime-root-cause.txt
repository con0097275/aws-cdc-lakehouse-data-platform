2. THE WRONG APICURIO ARTIFACT WAS STAGED  (the original killer)
--------------------------------------------------------------------------------
   ConfigException: Invalid value io.apicurio.registry.serde.avro.AvroConverter for
   configuration key.converter: Class ... could not be found

   versions.env stages apicurio-registry-serdes-avro-serde-2.6.2.Final.jar. That jar holds
   AvroKafkaSerializer / AvroKafkaDeserializer / AvroSchemaParser -- and NO converter:

     $ unzip -l apicurio-serde.jar | grep .class
       io/apicurio/registry/serde/avro/AvroKafkaSerializer.class
       io/apicurio/registry/serde/avro/AvroKafkaDeserializer.class
       ... no AvroConverter anywhere

   In Apicurio 2.x the Kafka Connect CONVERTER is a DIFFERENT artifact,
   apicurio-registry-utils-converter, class io.apicurio.registry.utils.converter.AvroConverter.
   The repo staged the serde and configured a converter class that only exists in the
   converter artifact. This is OPEN-14 landing for real: the artifact list was never
   verified against a running worker.

   FIXED on the host: downloaded apicurio-registry-utils-converter-2.6.2.Final.jar (74 KB,
   contains io/apicurio/registry/utils/converter/AvroConverter.class) and pointed
   key.converter/value.converter at the correct class.
   REPO FIX STILL NEEDED: docker/cdc-runtime/versions.env must stage the converter artifact
   (URL + SHA256), and the worker properties template must use the utils.converter class.

3. THE MSK IAM JAR WAS NOT ON THE WORKER CLASSPATH
--------------------------------------------------------------------------------
   ConfigException: Invalid value software.amazon.msk.auth.iam.IAMClientCallbackHandler
   for configuration sasl.client.callback.handler.class

   plugin.path feeds ISOLATED plugin classloaders; the worker's OWN Kafka clients resolve
   the SASL callback handler from the SYSTEM classpath, which /opt/connect-plugins/libs is
   not on.

   A CLASSPATH env var was tried first and made things worse -- it REPLACED the image's
   classpath instead of appending, so jvm.classpath became only our four jars and Connect
   lost its own dependencies. Reverted.

   FIXED by mounting the jar where the image's classpath already looks:
     - /opt/connect-plugins/libs/aws-msk-iam-auth.jar:/usr/share/java/kafka/aws-msk-iam-auth.jar:ro

5. THE MSK IAM JAR WAS NOT IN THE APICURIO IMAGE EITHER
   The apicurio service declared SASL_SSL / AWS_MSK_IAM / IAMLoginModule /
   IAMClientCallbackHandler -- correctly -- but had NO volume mounts, so
   software.amazon.msk.auth.iam.IAMLoginModule was not on its classpath at all.
   Apicurio is a Quarkus FAST-JAR started with `java -jar`, so CLASSPATH is ignored and
   dropping a jar into /deployments/lib does not join the manifest classpath.
   FIXED: mount the jar and append it to the BOOT classpath, which `java -jar` does honour:
       JAVA_OPTS_APPEND: -Xbootclasspath/a:/opt/msk/aws-msk-iam-auth.jar
       volumes: /opt/connect-plugins/libs/aws-msk-iam-auth.jar:/opt/msk/...:ro
   VERIFIED in /proc/1/cmdline, and the log now has ZERO ClassNotFound/LoginException.
   restarts went 47 -> 0.
