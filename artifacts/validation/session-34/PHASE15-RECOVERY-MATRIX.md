## The invariant every row defends

**A watermark advances only behind a run that completed AND validated.**
`ops_client.finish_successfully` is the only path to `advance_watermark`, it runs
step 4 (watermark) before step 5 (SUCCEEDED), and `fail()` carries the comment
"there is no code path from here to advance_watermark". Cases 8, 9, 10 and 13
attack that invariant from four directions and it holds in all four.

## What is enforced structurally, not by convention

- **Illegal status transitions raise.** `RUNNING -> SUCCEEDED` is refused; a run
  must pass through `VALIDATING`, so success cannot be declared without the
  validation step having been entered (asserted in case 10).
- **`CheckpointInspector` has no `delete()`** and must not gain one. Discarding a
  checkpoint replays or skips data depending on where the offsets sat, so it is an
  operator decision behind `scripts/streaming-reset.sh` — dry-run by default, a
  typed phrase, and it MOVES rather than deletes (case 16).
- **Unknown dbt vars are rejected before dbt starts** (case 3). dbt silently
  ignores a var no macro reads, so an unchecked typo looks like a working run.
  Phase 14 hit this twice for real.
- **A dependency cycle fails at compile time** (case 18), not at run time.

## Not covered here

Airflow orchestrates none of this (`enable_airflow=false`, OPEN-28), so retry
BACKOFF, pool exhaustion and scheduler-level concurrency are unproven. What is
proven is that the framework's own guards do not depend on the scheduler for
correctness — case 14 exists precisely because `max_active_runs=1` does not cover
a manual trigger, a retry of a stuck task, or a dead worker.
